# Question 1: Binary vs Ternary Search

## Problem Statement
In binary search, an $n$ element list is divided into nearly two equal halves, while in ternary search, it is divided into nearly three equal intervals. Then the search will be in one of the intervals. 
The objective is to design and implement a C program to search for an element $x$ in a sorted list of size $n$ using both algorithms, and to justify and validate that **binary search is strictly better than ternary search**.

---

## Theoretical Justification
At first glance, ternary search seems faster because it reduces the search space by $1/3$ instead of $1/2$, resulting in a shorter recursion tree height: $\log_3 n$ vs $\log_2 n$. However, algorithmic efficiency depends on the total number of operations (comparisons), not just the height of the tree.

**1. Binary Search Comparisons:**
In the worst case, binary search makes up to **2 comparisons** per level (one to check equality, one to determine the half).
*   Worst-case comparisons: $\approx 2 \log_2 n$

**2. Ternary Search Comparisons:**
Ternary search uses two mid-points. In the worst case, it makes up to **4 comparisons** per level (two for equality checks, two for range checks).
*   Worst-case comparisons: $\approx 4 \log_3 n$

**Mathematical Proof:**
To compare them, we convert the base of the logarithm:
$$4 \log_3 n = 4 \left( \frac{\log_2 n}{\log_2 3} \right) \approx 4 \left( \frac{\log_2 n}{1.585} \right) \approx 2.52 \log_2 n$$

Since **$2.52 \log_2 n > 2 \log_2 n$**, Ternary Search performs approximately **26% more comparisons** than Binary Search in the worst-case scenario. Therefore, Binary Search is theoretically better.

---

## Empirical Validation (Implementation Details)
The provided C program (`q1.c`) validates this theoretical claim through rigorous empirical testing:

1. **Test Oracle & Cross-Validation:** Every search result is cross-checked against a standard linear search to ensure absolute correctness.
2. **Random Probing:** For each array size ($N = 15$ to $65535$), the program runs 400 random probes. It alternates between searching for elements that exist in the array and elements that do not (forcing the worst-case path).
3. **Comparison Tracking:** A counter strictly tracks the number of element comparisons made during each search, capturing both Average Case and Worst Case metrics.
4. **Data Export:** The results are exported to `q1_data.csv` for graphical visualization.

### Results
The execution output perfectly aligns with the mathematical model. The ratio of Worst-Case Ternary Comparisons to Worst-Case Binary Comparisons consistently converges to **$\approx 1.26$** (a 26% overhead).
